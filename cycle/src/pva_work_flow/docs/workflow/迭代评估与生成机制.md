# LLM 迭代评估与下一轮建议生成机制

本文档说明在闭环优化中，LLM 如何评估前一轮实验结果，并据此生成下一轮候选配方。核心管线分两步：**Diagnose（诊断）→ Generate（生成）**。

---

## 一、Diagnose：评估前一轮结果

入口函数：`run_diagnose()`（`workflow.py`）

### 1.1 数据组装

代码读取 `R{N}_results_filled.csv` 和 `R{N}_candidates.json`，为每个候选拼接三个维度的结构化数据：

```
每个候选 →
  ├── key_formulation:  {pva_wt%, additives, FT cycles, post_soak_hours}
  ├── metrics:          {COF_mean, COF_std, wear_proxy, modulus, failure_type, 3次重复COF}
  └── friction_analysis:{pattern, plateau_ratio, asymmetry, cv_amplitude, stick_slip_score, stable_proportion}
```

打包为一个大 JSON 发送给 Diagnostician LLM（使用 `DIA_PROMPT`）：

```json
{
  "round_id": "R1",
  "constraints": {"load_N": 10, "medium": "DI_water", ...},
  "results": [ {...8个候选的完整数据...} ]
}
```

### 1.2 LLM 输出的结构化诊断

Diagnostician LLM 被要求输出 7 个字段。此外代码层额外计算 2 个字段（`branch_evaluations` 和 `convergence`），不会交给 LLM 生成：

| 字段 | 来源 | 含义 |
|------|:--:|------|
| `dominant_failure_modes` | LLM | 主要失效模式 + 证据 + 置信度 |
| `inferred_mechanisms` | LLM | 推断的机制假设 + 支持/反对证据 |
| `actionable_levers` | LLM | 可操作的优化杠杆 + 方向 |
| `best_candidates` | **代码** | R1: 按绝对 COF 排序；**R2+: 按 dCOF 排序（相对父节点改善最多的在前）** |
| `branch_evaluations` | **代码** | 每个子节点与其父节点的逐分支对比：`{candidate_id, parent_candidate_id, cof, dcof, verdict}` |
| `next_round_doe` | LLM+代码 | LLM 提因子方向，代码层 `_build_structured_doe()` 接管具体因子名和水平值 |
| `summary_for_generator` | LLM | 给 Generator 的文本摘要 |
| `candidate_repairs` | 代码 | 每个候选的性能分类 + 修复建议（per-branch） |
| `convergence` | 代码 | 5 项收敛指标的逐项检查结果 + 建议动作 |

其中 `branch_evaluations` 是树模式的核心评估字段。每条记录包含：

```json
{
  "candidate_id": "R2-03",
  "parent_candidate_id": "R1-01",
  "cof": 0.0683,
  "dcof": 0.001,
  "verdict": "flat"
}
```

`verdict` 判定规则：`dcof < -0.005` → `improved`，`dcof > 0.005` → `worsened`，其余 → `flat`。无父节点数据时 → `no_parent_data`。

输出文件：`R{N}_diagnosis.json`

### 1.3 代码层接管 DOE 因子构建

LLM 输出的 `actionable_levers` 只是文本（如 `"pva_wt_percent"`），代码层 `_build_structured_doe()` 通过映射表将其转换为稳定的因子定义：

```python
_LEVER_TO_DOE = {
    "pva_wt_percent":  → {"name": "pva_wt_percent",       "levels": ["8.0", "10.0", "12.0"]},
    "freeze_thaw":      → {"name": "freeze_thaw_cycles",   "levels": ["0", "1", "2"]},
    "post_soak_hours":  → {"name": "post_soak_hours",      "levels": ["1", "2", "4"]},
    "crosslink":        → {"name": "crosslinker_concentration", "levels": ["low", "medium", "high"]},
    "additive":         → {"name": "additive_type",         "levels": [], "_dynamic": True},
    "plasticizer":      → {"name": "plasticizer_type",      "levels": [], "_dynamic": True},
}
```

带 `_dynamic` 标记的因子（如 `additive_type`），其 `levels` 从父轮配方的材料列表中自动提取。这一步解决了 LLM 命名漂移问题。

### 1.4 树模式下的逐分支 dCOF 评估

旧版批量模式中，`best_candidates` 是全局排名——按绝对 COF 排序，选出表现最好的几个配方。

树模式的核心评估逻辑是 **per-branch dCOF**：每个子节点和它的父节点对比，按 COF 变化量（dCOF = child_COF - parent_COF）评估分支表现。这一计算在 `run_diagnose()` 中完成：

```python
# workflow.py: run_diagnose()
# R2+ 时加载所有历史 COF，计算每个子节点相对真实父节点的 dCOF
_parent_cof = load_prior_cof_by_candidate(out_dir, round_idx)
# 读取范围: R1_results_filled.csv ... R{N-1}_results_filled.csv
for each child:
    parent_COF = _parent_cof[child.parent_candidate_id]
    dcof = child_COF - parent_COF
    verdict = "improved" if dcof < -0.005 else "worsened" if dcof > 0.005 else "flat"
```

这里有一个关键区分：**第 N 轮生成可以参考第 1 到第 N-1 轮的全部结果，但分支判定只和真实 `parent_candidate_id` 比较**。例如 `R3-04` 可以从 `R1-07` 继续扩展；系统会用所有历史结果作为统计/RAG 上下文，但 `R3-04` 的 dCOF 只计算 `R3-04 - R1-07`，不会默认和 `R2` 的全局最佳配方比较。

`best_candidates` 和 `branch_evaluations` 都基于 dCOF 排序：

| 字段 | R1（无父节点） | R2+（树模式） |
|------|---------------|---------------|
| `best_candidates` | 按绝对 COF 升序，取前 3 | 按 dCOF 排序（改善最多的在前），取前 3 |
| `branch_evaluations` | dcof 和 verdict 均为 `null` / `no_parent_data` | 每个子节点有完整的 dcof 和 verdict |

树模式下的父节点选择也不依赖 `best_candidates`——`constrained_doe.py` 在树模式下直接用 `--target_parent_id` 锁定父节点：

```python
# constrained_doe.py:246
if target_parent_id:                              # 树模式
    best_parent = by_id[target_parent_id]          # 直接锁定用户指定的父节点
else:                                             # 旧批量模式
    best_parent = next(_ranked_parents(...))       # 才用 best_candidates 排序
```

跨轮的分支生死（continue / rescue_candidate / kill）由 `formula_tree.py` 根据父子 COF 差值和实验备注推断，写入 `formula_branch_decisions.json`：

| dCOF | branch_status | 动作 |
|------|:--:|------|
| 子 < 父（COF 改善） | `continue` | 该分支可继续展开 |
| 子 ≥ 父（COF 恶化） | `rescue_candidate` | 给一次定向修复机会 |
| rescue 后仍恶化 | `kill` | 该分支停止扩展 |
| 无实验结果 | `pending` | 等待实验数据 |

`best_candidates` 在树模式下仅作为 **LLM 的参考上下文**（"全局来看哪些配方表现好"），不参与结构性决策。真正的迭代决策在 `formula_tree.py` 的 per-branch dCOF 评估。

### 1.5 收敛判断

Diagnose 阶段还运行 `check_convergence()`，对当前轮最佳候选做 5 项定量检查，结论写入 `diagnosis.json` 的 `convergence` 字段。

## 二、Generate：根据诊断生成下一轮候选

入口函数：`run_generator()`（`generator.py`）

### 2.1 R1（首轮）

R1 没有前一轮数据，走 `GEN_PROMPT_R1`，候选数量自动取 `--tree_initial_roots`（默认 10），作为后续树优化的独立 root 节点。支持两种模式：

- **LLM 生成**（默认）：由模型根据 prompt 自主生成初始 root 配方
- **外部配方**（`--use_external_r1`）：使用预先准备好的 `R1_candidates.json`，跳过 LLM 生成——适用于人工设计第一轮配方的场景

### 2.2 R2+：结构化 Prompt 注入

`build_generator_prompt()` 构建 prompt 时，在前端注入四张硬数据表——LLM 看到的是精确数值和硬边界，不是模糊摘要：

```
┌────────────────────────────────────────────────┐
│ === R1 EXPERIMENTAL RESULTS (REAL DATA) ===    │  ← 来自 results_filled.csv
│ ID      COF     pattern     wear   modulus     │
│ R1-01   0.029   irregular   38.8   1.78        │
│ R1-02   0.031   irregular   12.3   -           │
│ ...                                            │
│                                                │
│ === PARENT CANDIDATE FORMULATIONS ===          │  ← 来自 candidates.json
│ R1-04: PVA=12%, network=chemical/ga_hcl,      │
│        additives=[CMC 1.0%], FT=0, soak=1h    │
│                                                │
│ === DOE BOUNDARIES — PICK FROM THESE ===       │  ← 来自 diagnosis.json
│ pva_wt_percent: [8.0, 10.0, 12.0]             │
│ freeze_thaw_cycles: [0, 1, 2]                 │
│ additive_type: [HA, CMC, DMSO, Mucin]         │
│                                                │
│ === ALLOWED MATERIALS ===                      │  ← 来自 materials_en.csv
│ PVA, DMSO, Sodium Hyaluronate, CMC, ...       │
└────────────────────────────────────────────────┘
```

### 2.3 额外上下文

Prompt 末尾还追加三块动态上下文：

| 上下文 | 来源 | 作用 |
|--------|------|------|
| KPI 趋势 | `kpi_log.json` | `R1: best_cof=0.029 → R2: best_cof=0.035. WARNING: COF INCREASED` |
| 审计失败清单 | `R{N}_audits.json` | `DO NOT repeat: [3x] missing material amount, [2x] baseline changed` |
| R1 原始诊断 | `R1_diagnosis.json` | R3+ 时强制注入，防止多轮信息衰减 |
| 收敛状态 | `R{N}_diagnosis.json` | `NOT converged. Failed: COF > 0.02, modulus out of range` |
| 跨树统计 | `tree_statistics.json` | 前几棵树的变量效果、kill_rate、rescue_success_rate |
| 树报告/实验汇总 | `SIMPLE_TREE.md`, `GLOBAL_TREE_SUMMARY.md`, `EXPERIMENT_FORMULA_SUMMARY.md` | 每棵 root 树的简略过程、全局树总览、材料配方与实验步骤汇总 |

### 2.4 R2+ 的 3-Agent 流水线

当前 R2+ 默认走 3-Agent 流水线（`pipeline_agents.py:run_three_agent_pipeline()`），将一次复杂的生成任务拆为三次独立的 LLM 调用：

```
Agent 1: Audit           Agent 2: DOE Planning       Agent 3: Formula Generation
┌────────────────┐      ┌────────────────────┐      ┌──────────────────┐
│ System:         │      │ System:             │      │ System:           │
│ AUDIT_AGENT     │      │ DOE_PLANNING_AGENT  │      │ FORMULA_AGENT     │
│                │      │                    │      │                  │
│ Input:          │      │ Input:              │      │ Input:            │
│ R1 配方 + 结果  │ ──→  │ audit_agent.json    │ ──→  │ 继承关系表         │
│                │      │                    │      │                  │
│ Task:           │      │ Task:               │      │ Task:             │
│ 找规律、评优劣   │      │ 设计实验结构         │      │ 写可执行配方       │
│                │      │                    │      │                  │
│ Gate:           │      │ Gate:               │      │ Gate:             │
│ 无（纯分析）     │      │ inner_rules 4条件    │      │ self-review 10题   │
│                │      │ black_box_risk < 4   │      │ 变量不得超出表范围  │
│                │      │                    │      │                  │
│ Output:         │      │ Output:             │      │ Output:           │
│ audit_agent.json│      │ doe_plan.json       │      │ candidates (raw)   │
└────────────────┘      └────────────────────┘      └──────────────────┘
   ~10KB context            ~5KB context               ~4KB context
   单任务聚焦                单任务聚焦                   单任务聚焦
```

**Agent 1 — Audit Agent**：只分析数据，不设计配方。Prompt 中有 8 条 ANALYSIS REQUIREMENTS：

1. 按综合质量（COF↑, stable_proportion↓, wear↓）排序所有候选
2. 识别系统性摩擦模式问题（全部 irregular/asymmetric → 系统性缺陷）
3. 对比添加剂效果（哪个添加剂 COF 更低、稳定性更好？引用具体数值）
4. 检查相关性（modulus vs COF？soak vs stability？）
5. 每个候选分类为 `promising / needs_optimization / discard`
6. 提取跨候选规律（交联剂选择、添加剂效应、工艺参数）
7. 异常数据标记但不丢弃整轮
8. 禁止在数据非空时说 "data insufficient"

**Agent 2 — DOE Planning Agent**：生成继承关系表（硬骨架），被 `inner_rules` 4 条件门控：

1. 有明确父配方；树模式下由 `--target_parent_id` 锁定同一个真实父节点（禁止同轮自引用）
2. 树模式下本轮候选可以全部来自同一个父配方；非树批量模式才鼓励多个父配方分散风险
3. 设计类型在允许列表中（baseline / single_factor / local_opt / failure_verify / limited_exploration）
4. `black_box_risk < 4`

加上化学知识规则（Epoxy 需胺固化剂、UV 需光引发剂、Borax 自催化不需 HCl 等）。

**Agent 3 — Formula Generation Agent**：将继承表转换为完整配方。不能修改继承表中的 `candidate_id`、`parent_candidate_id`、`design_type`、`variables_changed`。在受限模式（`skeleton_source=code_constrained_doe`）下，代码直接 `deepcopy` 父配方并只应用 `variables_changed`，LLM 仅负责补充 `expected_mechanism`、`risks_and_mitigations` 等解释性字段。

### 2.5 生成后的代码层后处理

LLM 输出的候选经过 `generator.py` 中的后处理链（Plan A）：

```
raw candidates
  → canonicalize_candidate_materials()    # 材料名规范化
  → _auto_fix_process_steps_order()       # 步骤编号自动补全
  → apply_ratio_plan()                    # 20g batch 克数换算
  → _auto_generate_risks()                # 补齐 risks_and_mitigations
  → _auto_generate_expected_mechanism()   # 补齐机制描述
  → _auto_extract_doe_factors()           # 补齐 DOE 因子
  → _auto_fix_material_basis()            # 补齐 material.basis
  → 数值自动修正（soak≤4h, FT≤3, cycle_h≤2）
  → detect_changed_variables()            # 语义变量变化检测
  → validate_candidate_constraints()      # 硬约束校验
  → compute_prep_time_hours()             # 制备时间检查
  → 写入 tree_id/node_id/branch_status    # 树谱系字段
```

## 三、RAG 增强：让迭代决策随数据增长而变聪明

系统有两层独立的 RAG 机制，在每次迭代时将积累的历史经验注入 LLM prompt。随着实验数据增多，统计规律越来越可靠，LLM 的决策质量也随之提升。

### 3.1 第一层：实验记忆 RAG（`experiment_rag.py`）

每轮 3-Agent Pipeline 结束时，系统自动将所有候选写入 `experiment_records.jsonl`——一个不断增长的实验日志文件：

```python
# pipeline_agents.py — 每轮最后
for c in candidates:
    append_experiment_record(c, path=out_dir / "experiment_records.jsonl")
```

下一轮 Audit Agent 启动时，系统从该 JSONL 中做多路检索并注入 prompt：

```
build_rag_context_for_round()
  ├── retrieve_best_formulas(top_k=5)     → "历史上 COF 最低的 5 个配方"
  ├── retrieve_failed_formulas(top_k=5)   → "历史上失败/表现差的 5 个配方"
  ├── retrieve_by_variable(top_k=3)       → "与本轮关注变量相关的历史配方"
  └── retrieve_by_material(top_k=3)       → "与本轮关注材料相关的历史配方"
```

检索结果拼接为一段"历史教训"文本块，格式如下：

```
Relevant historical findings:
  1. R1-04 (parent=R1, type=local_optimization): PVA=12%, cl=Glutaraldehyde, COF=0.008, ...
     problem: asymmetric friction
  2. R1-06 (parent=R1, type=limited_exploration): PVA=12%, cl=Mucin, COF=0.034, ...

Implication for next round:
  - Best historical: R1-04 (COF=0.008)
  - Failed formulas to avoid repeating: R1-06
```

### 3.2 第二层：跨树统计 RAG（`tree_statistics.py`）

这是更关键的一层。每轮结束后自动调用 `build_tree_statistics()`，扫描所有已完成轮次的候选、结果和分支判定，汇总为三个维度的统计。

**数据来源**：统计模块会先读取当前 run 根目录下的 `R*_candidates.json`、`R*_results_filled.csv`、`formula_branch_decisions.json`；如果存在 `trees/root-*` 子目录，也会逐个读取每棵树目录里的同名文件，再合并成全局统计。这样既支持旧的平铺目录，也支持“每棵 root tree 一个目录”的实验记录方式。旧版 `trees/R1-*` 目录仍可读取，但新目录命名统一用 `root-*`。

```text
out_dir/
  R1_candidates.json
  R2_candidates.json
  tree_statistics.json
  trees/
    root-01/
      R1_candidates.json
      R2_candidates.json
      R1_results_filled.csv
      R2_results_filled.csv
    root-02/
      R1_candidates.json
      R2_candidates.json
      R1_results_filled.csv
      R2_results_filled.csv
```

不同树目录里可能都有 `R2-01` 这种局部编号，因此全局 `candidate_rows` 会记录 `artifact_source`，例如 `trees/root-01` 或 `trees/root-02`。统计时按来源分开读取分支判定，再在全局层面合并变量效果和树排名，避免候选 ID 互相覆盖。

编号分层规则：

```text
tree_id / tree_label      = root-01, root-02 ...  # 第几棵树
root_candidate_id         = R1-01, R1-02 ...      # 该树的真实根配方
candidate_id / parent_id  = R*-*                  # 真实轮次节点
```

因此 `root-04` 不能写进 `parent_candidate_id`；展开 `root-04` 时，代码会把它映射回真实父节点 `R1-04`。

**子-父配对提取项**：

```
对于每个子-父配对，提取:
  ├── changed_variables  → 做了哪些改动?
  ├── delta_cof          → 改动后 COF 变化了多少?
  └── branch_status      → 分支是 continue / rescue_candidate / kill?
```

**统计产出**：

| 统计表 | 内容 | 示例 |
|--------|------|------|
| 变量效果表 | 每个变量的 improvement_rate（改善概率）、mean_delta_cof（平均改善量）、kill_rate（致死率） | `pva_wt_percent: 改5次, 40%改善, 平均dCOF=-0.002, 20%致死` |
| 树排名表 | 每棵 root tree 的 best_cof、节点数、continue/kill 分布 | `R1-04: best_cof=0.022, 3节点, continue=2, kill=0` |
| Rescue 统计 | rescue 尝试次数 + 成功率 | `5次rescue, 2次成功, 成功率40%` |

写入三个文件：
- `tree_statistics.json` — 机器可读（供代码检索）
- `tree_statistics.md` — 人可读报告（供实验者审查）
- `tree_memory_cards.jsonl` — 可检索记忆卡片（供未来扩展）

同时，`tree_reports.py` 会额外写入三类人读报告：
- `trees/root-*/SIMPLE_TREE.md` — 每棵 root 树自己的简略迭代过程。每个节点写出 `candidate_id`、分支状态、COF（如已有结果）、`design_type`、改动变量和简要配方。
- `GLOBAL_TREE_SUMMARY.md` — 位于 tree 文件夹外，汇总所有 root 树，便于一次性检查本轮生成了多少棵树、每棵树展开到哪里。
- `EXPERIMENT_FORMULA_SUMMARY.md` — 位于 tree 文件夹外，按树和节点列出材料表、配方摘要、父节点和实验步骤，给实验执行和文章方法部分整理使用。

这些报告是“实验者视图”，不替代 `tree_statistics.json/md` 的统计 RAG 功能；统计文件给模型和统计分析用，报告文件给人快速审查和复盘用。

重新生成某一轮时，推荐使用归档式 regenerate，而不是手动删除旧文件：

```bash
bash scripts/pva_vllm.sh --regenerate_all_trees 2
bash scripts/pva_vllm.sh --regenerate_tree root-04 --round 2
```

`--regenerate_all_trees N` 会逐个进入 `trees/root-*`，把对应 `R{N}_*` 生成产物移动到该树目录下的 `archive/R{N}_timestamp/`，再重新运行 generate + prepare。`--regenerate_tree root-04 --round N` 只处理指定初始配方树。这样旧候选、旧 DOE 和旧模板可追溯，同时新一轮报告会自动刷新。

### 3.4 知识积累的动态过程：越跑越聪明

```
第 1 棵树 (R1-01):
  experiment_records.jsonl: 10 条记录
  tree_statistics.json:     tree_count=1, 无跨树对比
  → Audit Agent 没有历史参考, 全靠当前数据判断

第 2 棵树 (R1-02):
  experiment_records.jsonl: 14 条记录
  tree_statistics.json:     tree_count=2, 变量效果表初具雏形
  → Audit Agent 看到: "post_soak_hours 的 improvement_rate=0.67 最高"
  → 生成建议偏向延长浸泡时间

第 3-4 棵树:
  experiment_records.jsonl: 20+ 条记录
  tree_statistics.json:     variable_stats 中某些变量 kill_rate 开始凸显
  → Audit Agent 看到: "freeze_thaw_cycles 的 kill_rate=0.5, 谨慎增加 FT"
  → 生成建议避开高风险改动

第 5-8 棵树:
  experiment_records.jsonl: 30+ 条记录
  tree_statistics.json:     rescue_success_rate、树排名等宏观指标稳定
  → Generator 看到: "R1-04 的 best_cof 最低, CMC 体系最有前途"
  → 新树优先复用历史上 improvement_rate 高、kill_rate 低的变量方向
```

### 3.5 核心约束：统计共享 ≠ 谱系混合

RAG 提供的统计先验**不改变 `parent_candidate_id` 继承关系**。第 5 棵树仍然从自己的 root 配方出发，每个子节点只继承自己的父节点。统计知识是"建议"（"历史上这么做更可能改善"），不是"血缘"（"你爸是谁"）。

这一原则确保了：
- 每棵树内部的因果关系链保持清晰（单父节点继承）
- 树间的统计学习不破坏局部优化的可解释性
- 后续树可以安全地从前几棵树的失败中学习，而不会继承它们的错误谱系

## 四、完整数据流总览（含 RAG）

```
R{N} 实验完成后:

  Bruker CSV ─→ results_filled.csv ─┐
                                     ├─→ run_diagnose() ─→ LLM 分析 ─→ R{N}_diagnosis.json
  candidates.json ───────────────────┘       ↑                       ↓
                                      结构化 JSON               {failure_modes,
                                      (含摩擦模式/平台比        levers,
                                       /粘滑/不对称性)         branch_evaluations,
                                                               best_candidates,
                                                               next_round_doe,
                                                               summary, repairs,
                                                               convergence}

  R{N}_diagnosis.json ─┐
  kpi_log.json ────────┤
  results_filled.csv ──┤
  父配方 candidates ───┼─→ build_generator_prompt() ─→ 3-Agent Pipeline ─→ R{N+1}_candidates.json
  材料白名单 ──────────┤       ↑                              ↑
  审计失败记录 ────────┘   四张硬数据表               + 代码层后处理链
                           + KPI趋势/审计失败清单
                           + R1原始诊断(R3+)
                           + 跨树统计RAG
```

核心设计原则：**LLM 不是对着模糊摘要凭空发挥**。它看到的是精确的实验数据表 + 硬 DOE 边界 + 代码生成的继承骨架。LLM 的角色是解释数据和补充细节，硬约束由代码层保证。
